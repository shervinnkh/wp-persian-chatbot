# API‌های ورودی افزونه (سرور هوش مصنوعی ← افزونه)

این پوشه همهٔ API‌هایی را نگه می‌دارد که **سرور هوش مصنوعی روی سایت‌ها صدا می‌زند** (برعکسِ `includes/Rest` که برای پنل مدیر است).
اولین کاربرد: پردازش یک رکورد ممکن است ۵ دقیقه (یا بیشتر) طول بکشد؛ سرور بعد از پایان، **نتیجه را به افزونه خبر می‌دهد** و افزونه `ai_status` رکوردها را `2` (پردازش‌شده) می‌کند.

نسخهٔ قرارداد: `1` — فایل ماشین‌خوان: [`openapi.yaml`](openapi.yaml)

---

## ۰. خلاصهٔ ساده (وب‌هوک یعنی چه؟)

«وب‌هوک» فقط یعنی **تماس برگشتی**؛ هیچ اتصال دائمی یا پیچیده‌ای بین سرور و سایت وجود ندارد و سرور هم درگیر سایت نمی‌ماند:

1. افزونه یک رکورد (محصول، متن، فایل…) را برای سرور می‌فرستد. سرور فوراً می‌گوید **«۲۰۰ — گرفتم»** و کار را در صف خودش می‌گذارد. (ارتباط همین‌جا بسته می‌شود.)
2. افزونه همین‌که ۲۰۰ گرفت، رکورد را **«در حال پردازش»** (`ai_status = 1`) می‌کند. در پنل، به‌جای تیک یا آیکن هوش مصنوعی، یک **آیکن loading** می‌آید و روی آن نوشته می‌شود «در حال پردازش سمت سرور».
3. سرور هر وقت پردازش تمام شد (۵ دقیقه یا بیشتر) **یک پیام کوتاه** به سایت می‌زند: «کار فلان رکورد تمام شد» (`POST /ai/results`).
4. افزونه رکورد را **«پردازش‌شده»** (`ai_status = 2`) می‌کند و در پنل **آیکن هوش مصنوعی** جای loading می‌آید.

یعنی سرور فقط دو کار می‌کند: «گرفتم» (۲۰۰) و بعدها «تمام شد» (یک POST). بقیه‌اش (امضا، تلاش مجدد، …) در بخش‌های پایین فقط برای ایمنی و پایداری است.

### وضعیت رکورد (`ai_status`)

| مقدار | معنی | در پنل مدیر | چه کسی عوض می‌کند |
|---|---|---|---|
| `0` | هنوز به سرور داده نشده (یا ارسال ناموفق بود) | تیک | — |
| `1` | افزونه فرستاد و سرور **۲۰۰** داد؛ منتظر نتیجه | آیکن loading + «در حال پردازش سمت سرور» | افزونه، همان لحظهٔ پاسخ ۲۰۰ (`AiBackend::send`) |
| `2` | سرور پردازش را تمام کرد و **خبر داد** | آیکن هوش مصنوعی | وب‌هوک `POST /ai/results` با `status: "trained"` (`Apis\Results::apply`) |

> ⚠️ تا نسخهٔ `0.5.16` مقدار `1` یعنی «آموزش‌دیده» بود. از `0.5.17` «آموزش‌دیده» = `2` است (رکوردهای قدیمی هنگام ارتقا خودکار از ۱ به ۲ منتقل می‌شوند).

پنل مدیر خودش هر ۸ ثانیه (فقط وقتی رکوردی «در حال پردازش» است و تب مرورگر باز است) از **خود افزونه** وضعیت را می‌پرسد (`GET /paia/v1/ai-status`، فقط برای مدیر لاگین‌کرده؛ ربطی به سرور هوش مصنوعی ندارد) تا بدون رفرش صفحه، آیکن بعد از وب‌هوک عوض شود.

---

## ۱. الگوی کلی (وب‌هوک + بازبینی)

```
افزونه ── POST {api_url}/…  { event, id, rev, data, callback:{url,…} } ──▶ سرور   (فوراً 200/202 + job_id)
افزونه: ai_status = 1 (در حال پردازش؛ آیکن loading)
                                                                           │ صف + پردازش (۵ دقیقه …)
افزونه ◀── POST {callback.url}  { results:[{id,status,rev}] } + امضا HMAC ──┘
افزونه: ai_status = 2 (پردازش‌شده)  →  200
```

این همان الگوی استاندارد وب‌هوک است (Stripe / GitHub / Shopify). دو قاعدهٔ مهم:

1. **وب‌هوک مسیر سریع است، نه تنها منبع حقیقت.** سایت‌ها ممکن است پشت Cloudflare/WAF، رمز staging، localhost یا هاست ضعیف باشند و وب‌هوک نرسد.
   پس سرور باید (الف) تلاش مجدد داشته باشد و (ب) افزونه بعداً بتواند وضعیت را **بپرسد** (بخش ۶). هر دو مسیر به یک تابع (`Apis\Results::apply`) می‌رسند.
2. **همه‌چیز ایدمپوتنت است.** ارسال دوبارهٔ یک نتیجه ضرری ندارد.

## ۲. سرور از کجا بفهمد به کدام آدرس بزند؟

افزونه خودش آدرس را می‌گوید: در **هر** درخواستی که به سرور می‌فرستد (send / train / delete) شیء `callback` هست
(ساختهٔ `Apis\Callback::descriptor()`):

```json
"callback": {
  "api_version": 1,
  "url": "https://shop.example.com/wp-json/paia/v1/ai/results",
  "ping_url": "https://shop.example.com/wp-json/paia/v1/ai/ping",
  "site_url": "https://shop.example.com",
  "signature": "hmac-sha256",
  "max_results": 500
}
```

- آدرس با `rest_url()` ساخته شده، پس برای سایت بدون پیوند یکتا (`?rest_route=`) و سایت در زیرپوشه هم درست است.
- سرور `callback.url` را **کنار job ذخیره می‌کند** و بعد از پایان همان را صدا می‌زند؛ لازم نیست جدول دستی از آدرس سایت‌ها داشته باشد.
- شناسایی سایت: همان `api_key` (هر سایت یک کلید). کلید به یک سایت/هاست **قفل** می‌شود (بخش ۳).

## ۳. امنیت

### امضا (افزونه این‌ها را بررسی می‌کند)

| هدر | مقدار |
|---|---|
| `X-PAIA-Timestamp` | زمان یونیکس (ثانیه، UTC) |
| `X-PAIA-Signature` | `sha256=` + hex از `HMAC_SHA256(api_key, "{timestamp}.{بدنهٔ خام}")` |
| `X-PAIA-Delivery` | شناسهٔ یکتای ارسال (UUID)؛ در تلاش مجدد **همان** مقدار |

- امضا روی **بایت‌های دقیقاً ارسال‌شده** است؛ JSON را یک‌بار سریالایز کنید و همان بایت‌ها را بفرستید (`content=body`، نه `json=`).
- اختلاف زمان مجاز: ±۵ دقیقه (ضد replay). در خطا `server_time` سایت برگردانده می‌شود.
- کلید روی شبکه نمی‌رود. برای جداکردن کلید امضا از کلید دسترسی، در افزونه فیلتر `paia_api_secret` هست.

```python
import hashlib, hmac, json, time, uuid, httpx

def deliver(callback_url: str, api_key: str, payload: dict) -> httpx.Response:
    body = json.dumps(payload, ensure_ascii=False, separators=(",", ":")).encode()
    ts = str(int(time.time()))
    sig = "sha256=" + hmac.new(api_key.encode(), ts.encode() + b"." + body, hashlib.sha256).hexdigest()
    return httpx.post(
        callback_url, content=body,
        headers={"Content-Type": "application/json", "X-PAIA-Timestamp": ts,
                 "X-PAIA-Signature": sig, "X-PAIA-Delivery": payload["delivery_id"]},
        timeout=httpx.Timeout(10.0, connect=3.0), follow_redirects=False,
    )
```

### محافظت سرور در برابر SSRF (وظیفهٔ تیم سرور)

سرور آدرسی را صدا می‌زند که «کلاینت» داده است؛ پس:
- فقط `https` (در توسعه استثنا)؛ فقط پورت‌های ۴۴۳/۸۴۴۳؛
- **هاست `callback.url` باید با هاستِ سایتی که کلید به آن قفل شده یکی باشد** (در اولین اتصال ثبت و قفل شود)؛
- DNS را resolve کنید و IP‌های خصوصی/loopback/link-local (`10.*`، `127.*`، `169.254.*`، `192.168.*`، `::1` …) را رد کنید؛ به IP بررسی‌شده وصل شوید (ضد DNS-rebinding)؛
- ریدایرکت دنبال نشود؛ پاسخ را حداکثر چند KB بخوانید.

## ۴. مسیرها

پایه: `{site}/wp-json/paia/v1` (یا `{site}/?rest_route=/paia/v1/…` وقتی پیوند یکتا خاموش است — همان `callback.url` را استفاده کنید).

### `GET /ai/ping`
دست‌دادن و سنجش سلامت. بدنه ندارد (امضا روی رشتهٔ خالی). هنگام اولین اتصال سایت و دوره‌ای صدا بزنید؛ **زمان پاسخ را ثبت کنید** (برای کنترل سرعت ارسال به سایت‌های کند).

```json
{ "ok": true, "api_version": 1, "plugin_version": "0.5.17", "wp_version": "6.8",
  "site_url": "https://shop.example.com", "callback_url": "https://shop.example.com/wp-json/paia/v1/ai/results",
  "max_results": 500, "time": 1790000000 }
```

### `POST /ai/results`
اعلام نتیجهٔ پردازش یک **دسته** رکورد (حداکثر ۵۰۰ مورد و ۱ مگابایت).

```json
{
  "job_id": "j_8f3a",
  "delivery_id": "6b1c0a52-…",
  "results": [
    { "id": "product:23",  "status": "trained",   "rev": "5d41402abc4b2a76b9719d911017c592" },
    { "id": "blog:45",     "status": "failed",    "error": "متن خالی است" },
    { "id": "text:1790000000123", "status": "trained", "rev": "…" },
    { "id": "file:1790000000456", "status": "untrained" }
  ]
}
```

| فیلد | توضیح |
|---|---|
| `id` | شناسهٔ رکورد همان‌طور که افزونه فرستاد: `product:23`، `blog:5`، `page:7`، `*_taxonomies:all`، `site:1`، `text:…` (متن دستی)، `file:…` (فایل آپلودی) |
| `status` | `trained` ← `ai_status = 2` (پردازش‌شده؛ آیکن هوش مصنوعی) · `untrained` ← `ai_status = 0` (مثلاً بعد از حذف بردارها در سرور) · `failed` ← اگر رکورد «در حال پردازش» (`1`) بود به `0` برمی‌گردد (تا آیکن loading برای همیشه نماند) و خطا لاگ می‌شود؛ رکورد پردازش‌شده (`2`) دست نمی‌خورد |
| `rev` | **همان مقداری که افزونه در درخواست ارسال داد**، بدون تغییر. اگر رکورد بعد از ارسال ویرایش شده باشد با نسخهٔ فعلی نمی‌خواند و نتیجه `stale` نادیده گرفته می‌شود (رکورد ویرایش‌شده اشتباهاً «آموزش‌دیده» نمی‌شود). برای `untrained`/`failed` لازم نیست |

پاسخ موفق `200`:

```json
{ "ok": true, "delivery_id": "6b1c0a52-…", "applied": ["product:23", "text:1790000000123", "file:1790000000456"],
  "ignored": [ { "id": "blog:45", "reason": "not_found" } ] }
```

دلایل `ignored`: `not_found` (رکورد دیگر نیست؛ مثلاً از سایت حذف شد) · `stale` (بعد از ارسال ویرایش شده؛ نسخهٔ تازه جداگانه ارسال می‌شود) · `invalid_id` · `invalid_status`.
**این‌ها خطا نیستند؛ دوباره نفرستید.** تلاش مجدد با همان `X-PAIA-Delivery` پردازش دوباره نمی‌شود (`{"ok":true,"duplicate":true}`).

### کدهای خطا و رفتار سرور

| کد | معنی | کار سرور |
|---|---|---|
| `200` | گرفته شد | تمام |
| `400` `paia_bad_json` / `paia_no_results` / `paia_too_many` | بدنه ناقص | **تلاش مجدد نکنید**؛ باگ سمت سرور است (لاگ کنید) |
| `401` `paia_bad_signature` | کلید یا بدنه اشتباه | تلاش مجدد نکنید؛ وضعیت اتصال سایت را «نیازمند بررسی» کنید |
| `401` `paia_stale_timestamp` | ساعت سرور/سایت | با زمان درست دوباره امضا و یک‌بار تلاش کنید؛ `server_time` در پاسخ هست |
| `404` `rest_no_route` | چت‌بات سایت خاموش یا افزونه غیرفعال | ارسال را برای این سایت **متوقف** کنید (بازبینی دوره‌ای) |
| `413` | بدنه بزرگ‌تر از ۱ مگابایت | دسته را کوچک‌تر کنید |
| `503` `paia_not_configured` | `api_key` در افزونه خالی است | متوقف + بازبینی |
| `408` / `429` / `5xx` / timeout | مشکل موقت | **تلاش مجدد با backoff** (بخش ۵) |

## ۵. توصیه‌های سمت سرور (سایت کند، سایت‌های زیاد)

افزونه سبک است (بعد از امضا فقط چند `UPDATE` دسته‌ای)، اما بالاخره کل وردپرس بوت می‌شود (روی هاست ضعیف ۰٫۵ تا چند ثانیه). برای اینکه یک سایت کند سرور را نگه ندارد:

1. **هرگز وب‌هوک را داخل worker هوش مصنوعی صدا نزنید.** پایان پردازش فقط یک رویداد در صف «تحویل (delivery)» بگذارد؛ worker جدا و ارزان آن را بفرستد.
2. **timeout سخت:** connect ≤ ۳ ثانیه، کل ≤ ۱۰ ثانیه. معطل‌شدن بیشتر = شکست.
3. **یک ارسال همزمان برای هر سایت** (per-site concurrency = 1) و rate-limit ملایم؛ سقف سراسری worker جدا از worker‌های هوش مصنوعی.
4. **دسته‌ای کنید:** برای هر job (یا هر ۱۰–۳۰ ثانیه برای هر سایت) **یک** درخواست با چند `results`، نه یک درخواست برای هر رکورد.
5. **تلاش مجدد با backoff نمایی + jitter:** مثلاً ۳۰ث، ۲د، ۱۰د، ۱ساعت، ۶ساعت (حداکثر ~۸ بار)، فقط برای timeout/۴۰۸/۴۲۹/۵xx. با `Retry-After` هم احترام بگذارید. بعد از آن «dead» و وابسته به بازبینی.
6. **Circuit breaker برای هر سایت:** بعد از N شکست پیاپی، سایت «ناسالم» علامت می‌خورد؛ ارسال‌ها متوقف و فقط `ping` دوره‌ای (هر چند دقیقه) می‌رود تا برگردد.
7. از زمان پاسخ `ping` و ارسال‌های قبلی برای **تنظیم تطبیقی** سرعت/اندازهٔ دسته استفاده کنید.

## ۶. بازبینی (برای وب‌هوک‌های گم‌شده) — مرحلهٔ بعد

افزونه رکوردهای «ارسال‌شده ولی هنوز در حال پردازش (`ai_status=1`)» را دارد. توصیه: یک کرون وردپرس (هر ۱۰–۱۵ دقیقه، فقط وقتی چنین رکوردی هست) از سرور وضعیت job/رکوردها را بپرسد
(`POST {api_url}/jobs/status` با `ids`) و جواب را به **همان `Apis\Results::apply()`** بدهد.
قرارداد این endpoint سمت سرور هنوز تعریف نشده؛ فعلاً فقط آماده است که به آن وصل شود.

## ۷. درخواست ارسال (افزونه ← سرور)

هر رکوردی که افزونه برای سرور می‌فرستد (`AiBackend::send` / `train`؛ متن دستی، فایل، محصول، وبلاگ، برگه…):

```json
{ "event": "create|update", "id": "product:23", "rev": "<Apis\\Records::revision('product:23')>",
  "data": { … }, "callback": <Apis\Callback::descriptor()> }
```

`rev` و `callback` را سرور فقط نگه می‌دارد و بعداً برمی‌گرداند/صدا می‌زند.

**پاسخی که افزونه از سرور انتظار دارد:** هر کد `2xx` (پیشنهاد: `202` + `{ "job_id": "j_8f3a" }`) یعنی «گرفتم». افزونه با اولین `2xx` رکورد را «در حال پردازش» (`ai_status = 1`) می‌کند. هر کد دیگر/timeout یعنی ارسال ناموفق: `ai_status` همان `0` می‌ماند و در «لاگ سرور» خطا ثبت می‌شود.

### ⚠️ وضعیت فعلی: درخواست ساختگی

سرور هنوز ساخته نشده؛ پس `AiBackend::request()` **هیچ‌جا درخواست نمی‌فرستد** و خودش همیشه `200` برمی‌گرداند (`{"ok":true,"simulated":true,"job_id":"sim_…"}`). بنابراین الان با زدن «آموزش به هوش مصنوعی» (یا ذخیرهٔ متن با تیک آموزش، آپلود فایل، ذخیرهٔ خودکار محصول…) رکورد بلافاصله `ai_status = 1` می‌شود و آیکن loading می‌ماند تا وب‌هوک `trained` برسد.

وقتی سرور واقعی آماده شد فقط همین یک تابع عوض می‌شود (یا از فیلتر `paia_ai_backend_request` استفاده کنید):

```php
add_filter( 'paia_ai_backend_request', function ( $response, $path, $payload ) {
    $r = wp_remote_post( 'https://ai.example.com' . $path, array( 'timeout' => 10, 'body' => wp_json_encode( $payload ), 'headers' => array( 'Content-Type' => 'application/json' ) ) );
    return array( 'code' => (int) wp_remote_retrieve_response_code( $r ), 'body' => (array) json_decode( wp_remote_retrieve_body( $r ), true ) );
}, 10, 3 );
```

### تست بدون سرور (شبیه‌سازی وب‌هوک)

برای دیدن تبدیل loading ← آیکن هوش مصنوعی بدون سرور، همان `deliver()` بخش ۳ را با `callback.url` سایت و `api_key` تنظیمات صدا بزنید (شناسه‌ها را از رکوردهای «در حال پردازش» بردارید):

```python
deliver("https://shop.example.com/wp-json/paia/v1/ai/results", "API_KEY_SITE", {
    "job_id": "j_test", "delivery_id": str(uuid.uuid4()),
    "results": [{"id": "text:1790000000123", "status": "trained"}],   # rev را نفرستید تا مقایسه نشود
})
```

(بدون `rev`، نتیجهٔ `trained` بدون بررسی «کهنه بودن» اعمال می‌شود.)

## ۷-ب. دانلود فایل با لینک امضادار (سرور ← سایت) — از ۰.۵.۲۳

رکورد `file:*` به‌جای مسیر فایل، یک **لینک دانلود امضادار و کوتاه‌عمر** می‌فرستد؛ سرور هوش مصنوعی همان را GET می‌کند.

```jsonc
// POST /v1/knowledge/records  (شکل A)
{ "event": "create", "id": "file:1793261168782", "rev": "1793261168",
  "data": { "type": "file", "title": "راهنمای گارانتی", "original_name": "guide.pdf", "ext": "pdf",
            "size": 482113, "sha256": "<hex>",
            "download": { "url": "https://site/wp-json/paia/v1/ai/file?id=file:1793261168782&exp=1793264768&sig=<hex>",
                          "expires": 1793264768 } },
  "callback": { … } }
```
- `sig = hex( HMAC_SHA256( api_key, "paia-file\n{id}\n{exp}" ) )`؛ `id` و `exp` داخل امضا هستند و پیشوند `paia-file` آن را از امضای API جدا می‌کند. سرور هوش مصنوعی چیزی امضا/تأیید نمی‌کند، فقط لینک را باز می‌کند.
- **عمر ۱ ساعت** (تا نوبت صف و تلاش‌های مجدد برسد)؛ فیلتر `paia_file_link_ttl` (۵ دقیقه تا ۲۴ ساعت). منقضی ← `403 paia_link_expired`؛ سرور job را `failed` می‌کند (`download_link_expired`) و با «آموزش» دوباره لینک تازه ساخته می‌شود. کرون بازبینی هم برای `unknown` لینک تازه می‌سازد (`AiBackend::resend`).
- فقط همان یک فایل، فقط GET؛ `Content-Type: application/octet-stream`، `Content-Disposition: attachment`، `X-Content-Type-Options: nosniff`.
- `sha256` برای «تغییر نکرده» (بدون دانلود دوباره) و بررسی سلامت دانلود است. لینک در «لاگ سرور» نوشته نمی‌شود.
- `.doc` فرستاده نمی‌شود (سرور فقط pdf/docx/txt را استخراج می‌کند): «آموزش» خطای ۴۱۵ `paia_file_unsupported` می‌دهد.
- کد: `Apis\FileLink` (ساخت/تأیید)، `Apis\Endpoints\FileEndpoint`، `Sync\AiBackend::file_payload()`.

## ۸. ساختار پوشه

```
apis/
├─ README.md / openapi.yaml    قرارداد (این فایل)
├─ ApisModule.php              ثبت مسیرها (فقط وقتی چت‌بات روشن است)؛ فیلتر paia_api_endpoints
├─ Callback.php                شیء callback که افزونه به سرور می‌دهد؛ فیلتر paia_callback_url
├─ Records.php                 نسخه (rev) و ai_status دسته‌ای برای paia_items / paia_texts / paia_files
├─ Results.php                 هستهٔ اعمال نتیجه (ایدمپوتنت)؛ اکشن paia_ai_results_applied
├─ Auth/Signature.php          اعتبارسنجی امضای HMAC و زمان
└─ Endpoints/                  AbstractEndpoint، PingEndpoint، ResultsEndpoint
```

**افزودن API ورودی تازه:** کلاسی از `Endpoints\AbstractEndpoint` بسازید (`permission_callback` = `authorize`) و در فیلتر `paia_api_endpoints` اضافه کنید. هر رویداد را در لاگ سرور (`LogStore::add`) ثبت کنید.

## ۹. عیب‌یابی سایت‌هایی که وب‌هوک نمی‌گیرند

- `401 paia_bad_signature` با کلید درست: افزونه‌های امنیتی/پراکسی گاهی بدنه یا هدرها را تغییر می‌دهند.
- `403`/صفحهٔ چالش HTML: WAF یا Cloudflare مسیر `/wp-json/` را مسدود کرده؛ آی‌پی سرور را allow کنید یا به بازبینی تکیه کنید.
- `404`: پیوند یکتا خاموش است (از `callback.url` که `?rest_route=` دارد استفاده کنید) یا چت‌بات خاموش است.
- سایت پشت رمز (basic auth) یا localhost: وب‌هوک نمی‌رسد؛ فقط بازبینی کار می‌کند.

## ابزارهای هوش مصنوعی (Tool Calling): `/live/products` و `/live/tool` (از ۰.۵.۲۴)

سرور هنگام تولید پاسخ، اگر AI ابزار بخواهد این دو مسیر را **با همان امضای وب‌هوک** (`X-PAIA-Timestamp` / `X-PAIA-Signature`، بدنهٔ خام) صدا می‌زند. قرارداد کامل: `LIVE_TOOLS_API.md` (ریپوی سرور، `docs/`).

| مسیر | بدنه | پاسخ |
|---|---|---|
| `POST /paia/v1/live/products` | `{request_id, fields:["price","stock"], products:[{id}\|{name}] ≤5}` | `{ok:true, message:"<بلاک‌های کلید: مقدار>"}` |
| `POST /paia/v1/live/tool` | `{request_id, tool_id}` | `{ok:true, text}` یا `{ok:false, error}` |

- **HTTP 200** برای هر نتیجهٔ کاری (حتی «پیدا نشد»)؛ فقط امضای نامعتبر ۴۰۱. بدون کش (`no-store`).
- **محصولات:** فقط فیلدهایی که هم سرور خواسته و هم مدیر در «اطلاعات به‌روز ← تمام محصولات» روشن گذاشته (`price` = قیمت/قیمت اصلی/حراج، `stock` = وضعیت/تعداد/پیش‌سفارش، هر کدام با تیک خودش)؛ فقط محصول `publish` بدون رمز؛ id اولویت دارد، `name` با نرمال‌سازی ی/ک/ارقام؛ نتیجهٔ غیرقطعی = «چند نتیجه» (حداکثر ۳). ووکامرس (ساده/متغیر/گروهی/خارجی) + مسیر ساده برای EDD و مشابه.
- **ابزار داینامیک:** `tool_id` = شناسهٔ ردیف «اطلاعات تعریف‌شده» (فقط ردیف فعال)؛ متن هر بار زنده از دیتابیس؛ ارقام فارسی → لاتین.
- **سمت ارسال پیام** (`ReplyEngine::push`، فقط با `generate_ai_answer=true`): `live_product_datas` (از تیک‌های تب اطلاعات به‌روز)، `tools` (`[{id,title,description}]` ≤۳۰)، `page.id` و `notes` و (از ۰.۵.۲۶) `mark-the-conversation` (bool؛ مقدار تنظیم «مارک کردن چت توسط هوش مصنوعی»). اگر هوش مصنوعی نتواند جواب بدهد و این true باشد، سرور باید متن پاسخ را دقیقاً `Mark-Chat` برگرداند (هم در `ai_answer.message.content` همگام و هم در وب‌هوک `chat_answer`)؛ افزونه هیچ پیامی نشان نمی‌دهد و فقط گفتگو را مارک می‌کند.
- کد: `apis/Endpoints/Live*Endpoint.php`، `apis/Live/{LiveProducts,Text}.php`، `Database\LiveStore::ai_product_fields()/ai_tools()`.
